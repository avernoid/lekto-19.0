Technical Specification for AI & LLM

This Odoo module 'stock_move_date_adjust' regularises the 'date' field of stock.move records. In Odoo 19 valuation lives on stock.move and the Kardex / stock ledger reads stock.move.date. Transfers allow correcting that date via stock.picking.date_done, but scraps, inventory adjustments, manufacturing orders and disassemblies do not. The module adds a wizard (stock.move.date.adjust.wizard) reachable through contextual server actions bound to stock.move, stock.picking and stock.scrap, with two modes: fixed date and offset shift. It writes stock.move.date, keeps move lines aligned, syncs the source document header where one exists, and records original_date plus date_adjusted on the movement. It performs no revaluation: the stored 'value' of a done movement is never recomputed. Hard limits: future dates rejected, per-company maximum shift, and movements cannot be dated into a closed accounting period (validated with res.company._get_lock_date_violations). Access is gated by a dedicated group that no role implies. Manufacturing is covered by the companion bridge module stock_move_date_adjust_mrp. Compatible with Odoo 19 (Enterprise, Odoo.SH, Ganemo Online). NOT supported on Odoo Online due to custom code restrictions. Multi-language support for English and Spanish included.

Movement Dates

Regularise What No Document Lets You Edit

Correct the date of already processed stock movements coming from scraps, inventory adjustments and manufacturing, so your Kardex and stock ledger tell the truth. Preview everything before you apply. Nothing is revalued.

What We're Solving

----------------

The Dead End

In Odoo 19 a Transfer lets you unlock and fix its date. A Scrap, an Inventory Adjustment or a Manufacturing Order does not. Those movements are stamped at processing time and there is no way back through the interface, which leaves your stock ledger permanently wrong.

See It Before You Do It

One guided wizard resolves whatever you selected into its movements and shows them grouped by origin, with the document, the product, the current date and the new one. You confirm a table, not a leap of faith.

Fixed Date or Offset

Fixed date sends everything to one instant. Shift takes a reference pair -- a date you know and the date it should have been -- and applies only the gap between them, which preserves the intra-day spacing that was already correct. Flattening a month of movements onto a single second destroys information you wanted to keep.

Guarded By Design

A dedicated permission that no role implies, a mandatory reason, a permanent trace on the movement, and a hard block against dating anything into a closed accounting period. Powerful, not loose.

Setup & User Manual

Step-by-Step implementation

1. Configuration Guide

Nobody can use this until you say so. Two steps:

  • Go to Settings > Users & Companies > Users.
  • Open the user and set Movement Date Regularisation to Allowed.
  • Optional: in Settings > Inventory, set a Maximum Movement Date Shift in days.
  • Leave it at zero for no limit.
Smart Explainer: Grant the permission for the regularisation window and revoke it afterwards. Not even Inventory Administrator gets it by default, and users without it see no change anywhere in the interface.

2. Operating Manual (Workflow)

How the system behaves for the end-user:

Where To Find It

Open any Transfer, Scrap or the Moves Analysis list, select what you need and use the Actions menu (the gear next to the record name). Works on a single record or on a selection of hundreds.

The Preview

Before applying, the wizard lists every affected movement grouped by origin with its current and target date, plus a counter of how many documents are involved.

Honest Warnings

Non-blocking alerts tell you when a movement would end up before its own origin movement — the silent way a FIFO chain gets scrambled — when movements are not done, and when valuation entries will keep their date.

Documents Stay Consistent

The source document's own date follows: a Transfer's Date of Transfer, a Scrap's Date. You can switch that off if you only want the movements touched.

Always Reversible

The pre-regularisation date is stored in Original Date and never overwritten by later corrections. Restore Original Date puts it back. Filter the Moves list by Date Regularised to see everything you touched.

Traceable

A reason is mandatory, and a note lands in the chatter of the affected document with the full before/after table, the author and the real timestamp.

QA / User Testing Scenarios

Enterprise Validation Plan

Scenario 1: Nobody Sees It By Default

  1. Log in as a user with Inventory / Administrator but without the new permission.
  2. Open Inventory > Reporting > Moves Analysis and select a movement.
  3. Test: the Actions menu SHOULD NOT offer "Regularise Movement Dates".
  4. Grant Movement Date Regularisation = Allowed on that user and reload.
  5. Test: the action SHOULD now appear.

Scenario 2: Inventory Adjustment

  1. Set an on-hand quantity from Inventory > Operations > Physical Inventory and apply it.
  2. Find the resulting movement in Moves Analysis (filter Inventory).
  3. Run the action, choose Fixed date, set a past date, write a reason, Apply.
  4. Result: the movement AND its detailed operation lines carry the new date. Original Date holds the old one.

Scenario 3: Shift Preserves Spacing

Select two movements dated the same day at 08:00 and 15:30.

  • Choose Shift, set Move This Date = today and To This Date = one year ago.
  • Read Resulting Shift — it must say the movements go earlier — then Apply.
  • Result: both land one year earlier, still 7h30 apart.

Scenario 4: Closed Period Is Refused

Goal: prove the ledger of a filed period cannot gain movements.

  1. Set a Lock Date in Accounting covering last year.
  2. Try to regularise any movement into that period.
  3. Result: the system MUST refuse and name the lock date — even with "re-date the valuation entry" switched OFF.

Scenario 5: Restore & Audit

  1. Regularise a movement, then regularise it again to a different date.
  2. Test: Original Date MUST still show the very first value.
  3. Filter the Moves list by Date Regularised.
  4. Run Restore Original Date on it.
  5. Result: the date returns and the record leaves the filter.

FAQ & Troubleshooting

Common Resolutions

Does this recalculate my costs?

No. The stored value of a processed movement is never recomputed.

But note: the FIFO stack is queried by date, so re-dating does change which layers stay open and what future outgoing movements will cost. It is not a cosmetic operation.

What about the journal entry?

It stays where it is, unless you tick the dedicated option, which only appears when entries actually exist.

Detail: Odoo treats the date of a posted entry as unmodifiable, so the option does the only supported route: draft, clear the number, re-date, post. The entry is renumbered into the target period and leaves a sequence gap in the original. Reconciled, hash-protected and closed-period entries are refused.

Why can't I pick an inventory adjustment from the count screen?

Reason: Odoo stores no link between a quant and the movements that adjusted it.

Fix: go to Moves Analysis and filter by Inventory. Guessing the movement would risk re-dating the wrong one, so we refuse to guess.

Does it cover manufacturing?

Answer: Yes, through the companion bridge.

Detail: install stock_move_date_adjust_mrp to add Manufacturing Orders (components, finished goods and by-products) and Disassemblies. It installs itself automatically wherever Manufacturing is present.
