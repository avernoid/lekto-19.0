Technical Specification for AI & LLM

This Odoo module 'stock_move_date_adjust_mrp' is a bridge that extends 'stock_move_date_adjust' to Manufacturing. It depends on stock_move_date_adjust and mrp and installs automatically when both are present. It classifies stock.move records by raw_material_production_id, production_id and unbuild_id, adds contextual server actions on mrp.production and mrp.unbuild, and synchronises the order header: date_start from the component movements and date_finished from the finished and by-product movements. On an order already in state done this requires the 'force_date' context key, which the Odoo core otherwise reserves for its own work-order planner; without it mrp.production.write raises 'You cannot move a manufacturing order once it is cancelled or done.' Disassemblies (mrp.unbuild) are resolved through unbuild_id, which the core stamps on every movement, consumption included; the order's create_date is deliberately left untouched as it is an ORM audit field. Components are staggered one hour before the finished product so a consumption never shares a timestamp with the output it feeds. Compatible with Odoo 19 (Enterprise, Odoo.SH, Ganemo Online). NOT supported on Odoo Online due to custom code restrictions. Multi-language support for English and Spanish included.

MRP Date Bridge

Re-Date Manufacturing, Even When It's Done

Components, finished goods, by-products and disassemblies re-dated in a single pass, with the order header kept in sync. The companion bridge for Stock Move Date Regularisation. Nothing is revalued.

What We're Solving

----------------

The Locked Order

Once a Manufacturing Order is Done, Odoo refuses to move its Start Date and hides the End Date entirely. Its movements — the components consumed and the goods produced — are frozen on the day you validated, whatever day the work actually happened.

Both Sides, One Pass

Components, the finished product and every by-product travel together. Miss one side and your ledger shows the consumption in one month and the output in another — which is worse than the problem you started with.

Readable Order

Consumption is staggered one hour before the output. If everything landed on the same second, your ledger would lose the intra-day sequence and the tie-break would fall to internal record IDs.

Disassemblies Too

A Disassembly carries no date field at all — its movements inherit the moment the draft was created, not the moment it was validated. Both directions get corrected, and the record's creation stamp is left honest.

Setup & User Manual

Step-by-Step implementation

1. Configuration Guide

There is nothing to configure here. Two things to know:

  • This is a bridge: it installs by itself as soon as Manufacturing and Stock Move Date Regularisation are both present.
  • It adds no settings, no menus and no new views.
  • Permissions and limits are inherited from the base module.
  • Set Movement Date Regularisation = Allowed on the user who needs it.
Smart Explainer: Odoo normally refuses to move the dates of a completed Manufacturing Order. This bridge uses the very same mechanism the Odoo core uses internally when its work-order planner needs to rewrite those dates — no patching, no hacks.

2. Operating Manual (Workflow)

How the system behaves for the end-user:

Where To Find It

Open a Manufacturing Order or a Disassembly — or select several from their list — and use the Actions menu (the gear next to the record name). No new button, no new field, no new menu.

Grouped Preview

The preview separates Manufacturing - Components, Manufacturing - Finished Product and Disassembly, so you see at a glance that both sides of the operation are covered.

Order Header Follows

The order's Start Date takes the earliest component date and its End Date the latest output date, so the document never contradicts its own movements.

Automatic Staggering

With staggering on, components land on the chosen instant and the finished product one hour later. Turn it off to collapse everything onto a single timestamp.

Open Orders Behave Natively

On an order that is still open and planned, the native unplanning of work orders runs exactly as Odoo intends. The special path is reserved for orders already done or cancelled.

Traceable

A reason is mandatory, and a note lands in the chatter of the Manufacturing Order or Disassembly with the full before/after table, the author and the real timestamp.

QA / User Testing Scenarios

Enterprise Validation Plan

Scenario 1: A Done Manufacturing Order

  1. Confirm and complete a Manufacturing Order with at least two components.
  2. On the order form, note that Start Date is now read-only.
  3. Use Actions > Regularise Movement Dates, pick a past date, write a reason, Apply.
  4. Result: every component AND the finished product carry the new date, and the order's Start / End Dates follow.

Scenario 2: Staggering

  1. Repeat Scenario 1 with Stagger within each document ticked.
  2. Open Inventory > Reporting > Moves Analysis and filter by the order reference.
  3. Result: the components sit on the chosen instant and the finished product exactly one hour later.
  4. Untick the option and repeat: everything MUST collapse onto the same timestamp.

Scenario 3: By-Products

Add a by-product line to the Bill of Materials and produce again.

  • Run the action on the completed order.
  • Result: the by-product movement MUST appear in the preview under Manufacturing - Finished Product and be re-dated with the rest.

Scenario 4: Disassembly, Both Directions

Goal: confirm consumption and returned components both move.

  1. From the completed order, click Unbuild.
  2. Open the Disassembly and run the action with a past date.
  3. Result: the consumption of the finished product AND the return of every component carry the new date.
  4. Test: the Disassembly's technical Created on value MUST remain unchanged — it is an audit stamp, not an operation date.

Scenario 5: Open Orders Keep Native Behaviour

  1. Create a Manufacturing Order with work orders and plan it. Do not complete it.
  2. Run the action on it.
  3. Result: the dates move AND Odoo unplans the work orders, exactly as it does when you edit the date by hand. The special path applies only to orders already done or cancelled.

FAQ & Troubleshooting

Common Resolutions

Is bypassing the "done order" guard safe?

Yes. It uses the exact mechanism the Odoo core itself uses when its work-order planner rewrites those same dates.

Detail: no core file is patched and no guard is removed. Open, planned orders keep the native behaviour, unplanning included.

Why doesn't the Disassembly show a date?

Reason: Odoo's Disassembly model has no date field at all. Its movements inherit the record's creation stamp.

By design: we re-date the movements and leave Created on alone. Falsifying when a record was created would be worse than the problem being fixed.

Do I need to install this separately?

No. It is an auto-installing bridge.

Detail: as soon as Manufacturing and Stock Move Date Regularisation are both installed, this module comes in on its own. Nothing to configure.

Are work orders and costs affected?

Answer: Work-order durations are untouched, and nothing is revalued.

But note: the FIFO stack is queried by date, so re-dating does change which layers stay open and what future outgoing movements will cost. It is not a cosmetic operation.
