Technical Specification for AI & LLM

This Odoo module 'account_report_analytic_domain' adds an 'analytic_domain' computation engine to account.report.expression, the counterpart of the native 'domain' engine but running on account.analytic.line instead of account.move.line. A report line therefore aggregates the share of a journal item that was distributed to given analytic accounts, because account.analytic.line.amount already holds that share; the engine sums -amount so results keep the accounting balance sign and stay aggregatable through the 'aggregation' engine. Formulas are Odoo domains on analytic items: analytic plan columns, general_account_id and its account_type, code or tag_ids, partner_id, product_id, date, journal_id, and move_line_id for anything else. It translates the report's own option domain (dates and every date_scope, companies, journals, partners, forced_domain), renames account_id to general_account_id, applies the same currency table as the domain engine, supports groupby on any stored analytic field, and audits a cell by opening the matching analytic items. Two computed banners review the formula in the form. Subformulas: sum, -sum, sum_if_pos, sum_if_neg, count_rows. Requires account_reports (Enterprise). Compatible with Odoo 19 (Enterprise, Odoo.SH, Ganemo Online). Multi-language support for English and Spanish included.

Analytic Domain

Report lines built from analytic items

An expense of 1,000 split 20% Marketing / 30% Administration / 50% Management should show 800 on a line called "Administrative expenses". With the standard engine it shows 1,000. This one shows 800.

What We're Solving

----------------

The whole amount, or the share?

A report line built on journal items can filter by analytic distribution, but it always brings the full balance. Odoo does know how to prorate — its analytic group-by columns do — but only as extra columns, never as a line of your own report. This engine puts the prorated figure in the line.

No arithmetic to maintain

The module performs no distribution arithmetic. Each analytic item already carries its share of the journal item's balance, computed and rounded by Odoo itself when the entry was posted. The engine only adds them up, so your figures cannot drift from Odoo's.

The full domain vocabulary

Write an ordinary Odoo domain on the fields you already see in Analytic Items: the analytic account of a plan, the accounting account and its type, code or tags, the partner, the product, the journal, the date. Group several analytic accounts through a sub-plan instead of listing them one by one.

It behaves like a native line

Dates and every date scope, companies, journals, partners and currency conversion are taken from the report itself, with no configuration. The sign matches the accounting balance, so an analytic line adds up with ordinary lines through the aggregation engine, and clicking the figure opens the analytic items behind it.

Setup & User Manual

Step-by-Step implementation

1. Configuration Guide

Add a prorated line to any report in 4 steps:

  • Go to Accounting > Configuration > Reports and open or create your report.
  • Add a line and open its expression.
  • Set Computation Engine to Analytic Domain.
  • Write the domain and a subformula: sum, -sum, sum_if_pos, sum_if_neg or count_rows.
You are not on your own: choosing the engine reveals a guide listing your database's own analytic plans with the field name each one answers to — nobody can guess that the plan called "Cost Centres" is x_plan6_id — plus examples ready to copy.

2. Operating Manual (Workflow)

What the accountant gets, day to day:

A reviewer for every formula

A second banner reads the formula as it is typed and separates what will not work from what will be slow, because a broken condition matters more than a slow one and would otherwise be hidden by it.

Group without listing

Put several analytic accounts under a sub-plan and filter by it. A sub-plan shares its parent's field, so it groups accounts inside one dimension instead of adding another — and the list never rots when you add an account.

Unfold by anything

The report line's Group By works on any stored field of the analytic item: cost centre, accounting account, partner, product, journal — or two levels at once, such as accounting account and then cost centre.

Click the figure

Auditing a cell opens exactly the analytic items behind it, with the report's own period and filters applied, so any number on the report can be traced back to its entries.

It tells you when it cannot

Analytic items exist only for posted entries. Switching on "Include unposted entries" therefore cannot widen these lines, so the report says so with a warning instead of quietly disagreeing with the rest of the page.

Multi-company, one currency

Consolidated reports convert analytic lines through the same currency table the native engine uses, so an analytic line and an accounting line over the same entries agree to the cent.

QA / User Testing Scenarios

Enterprise Validation Plan

Scenario 1: The distributed share (the core test)

  1. Create an analytic plan, e.g. "Cost Centres", with three accounts: Marketing, Administration and Management.
  2. Post a journal entry with an expense line of 1,000 distributed 20% Marketing / 30% Administration / 50% Management.
  3. Create a report line "Administrative expenses", engine Analytic Domain, filtering the plan field for Administration and Management, subformula sum.
  4. Test: the line SHOULD read 800.
  5. Test: the same domain on the standard Odoo Domain engine reads 1,000 — that difference is the module.

Scenario 2: Grouping and drill-down

  1. On that line, set Group By to the analytic plan's field.
  2. Test: unfolding SHOULD show Administration 300 and Management 500, and NOT Marketing.
  3. Change Group By to general_account_id.
  4. Test: the same 800 SHOULD now break down by accounting account.
  5. Test: click the 800. The analytic items behind it SHOULD open, limited to the report's period.

Scenario 3: Grouping accounts without listing them

  1. Create a sub-plan "Structure" under "Cost Centres" and move Administration and Management into it.
  2. Replace the domain with one filtering the plan field by plan_id child_of that sub-plan.
  3. Test: the line SHOULD still read 800, with no account ids written by hand.
  4. Test: add a new account to the sub-plan and post to it. The line SHOULD pick it up with no change to the formula.

Scenario 4: Filtering on the accounting account

  1. Add ('general_account_id.account_type', '=', 'expense') to the domain.
  2. Test: the figure SHOULD NOT change, since the entry is an expense.
  3. Change it to 'income'.
  4. Test: the line SHOULD read 0.
  5. Test: a code prefix such as ('general_account_id.code', '=like', '60%') SHOULD behave the same way against your own chart of accounts.

Scenario 5: Period, draft entries and the assistant

  1. Narrow the report's period to a month that excludes the entry.
  2. Test: the line SHOULD read 0; widen it again and it SHOULD return to 800.
  3. Reset the entry to draft.
  4. Test: the line SHOULD read 0, because analytic items exist only for posted entries.
  5. Test: switch on "Include unposted entries". The report SHOULD show a warning explaining that these lines cannot widen.
  6. Test: type a nonsense field in the formula. The review banner SHOULD turn red and name the field.

FAQ & Troubleshooting

Common Resolutions

My line shows the whole amount, not the share

Reason: the expression is still on the standard Odoo Domain engine, which reads journal items and cannot prorate.

Fix: open the expression and set Computation Engine to Analytic Domain. The figure changes on the next refresh.

I filtered by account_id and got nothing

Reason: on an analytic item account_id is the analytic account of the project plan, not the accounting account. They happen to share a field name.

Fix: use general_account_id. The review banner detects this exact mistake and gives you the working spelling.

It will not let me group by auto_account_id

Reason: that field means "the analytic account of any plan". It is calculated on the fly, so there is no column to group by.

Fix: group by the field of the plan you actually mean. It is also the faster way to filter, and the assistant points at it by name.

Does it slow the report down?

Answer: no — it reads a smaller, well-indexed table.

Detail: the share was computed when the entry was posted, so nothing is recalculated at report time: one aggregate query per line, no rows loaded into memory. Each remark in the review banner also carries the measured cost of that way of writing the filter.
